# Natural Targets — RDO на готовых парах, без DIM в целях

## Коротко

**Статус: прогон завершён 29.10.2026, этапы 00–07, включая судью StrongREJECT.**
Итоги — [reports/results.md](reports/results.md).

Главный результат: компонента, построенная только по 20 RDO на готовых человеческих парах, без
участия DIM, снимает отказ по судье на 0.852 против 0.026 без аблации и статистически не
отличается от компоненты с DIM (Δ = −0.019, ДИ накрывает ноль). Компонента базового прогона —
другие запросы, другие цели — работает на наших запросах наравне со своей (0.872). Отклонение
нашей компоненты от общей оси двух прогонов неотличимо от отсутствия аблации.

Цели обучения RDO в базовом протоколе генерируются через DIM (`rdo.py:327-357`): ответ без
отказа — генерация Instruct при аблации DIM, отказ на безобидный запрос — при её прибавлении.
Поэтому сходимость RDO и DIM к общей компоненте $w$ — не независимое свидетельство. Здесь
RDO обучается на целях, где DIM не участвует вовсе: ответ без отказа взят готовым из
BeaverTails (человеческая разметка `is_safe`), слагаемое наведения отказа выключено
(`addition_lambda: 0`), `retain` — собственный ответ модели. Остальное — обычный протокол:
4 DIM + 20 RDO, общая компонента по 24 векторам, судья StrongREJECT.

Главное число: $|\cos|$ новой компоненты с $w$ базового прогона и $|\cos|$ каждого RDO с ним
против LOO-распределения обычных RDO (среднее ≈ 0.58).

Постановка, данные и границы — [idea.md](idea.md).

## Порядок прогонов

```
cd shared-refusal-component
STEPS=00 bash launch/qwen2.5-3b_beavertails-b1b5b6bv.sh            # сплиты, CPU
STEPS=01 GPU=0 bash launch/qwen2.5-3b_beavertails-b1b5b6bv.sh      # цели без DIM, DIM, 20 RDO
STEPS="02 04 05" bash launch/qwen2.5-3b_beavertails-b1b5b6bv.sh    # компонента, анализ, сходимость
STEPS=03 GPU=0 bash launch/qwen2.5-3b_beavertails-b1b5b6bv.sh      # аблация
STEPS=06 GPU=0 bash launch/qwen2.5-3b_beavertails-b1b5b6bv.sh      # генерация StrongREJECT
STEPS=07 bash launch/qwen2.5-3b_beavertails-b1b5b6bv.sh            # судья, с Mac
```

Карты на сервере заняты соседями, поэтому этапы 01–06 ставятся в очередь:
`scripts/wait_and_launch.sh` в tmux-сессии `fz-wait-bt` ждёт карту и запускает launch-файл сам.
Две поправки к ожиданию по умолчанию, обе из опыта 29.10.2026.

Опрос должен быть частым (`INTERVAL=10`): освободившуюся карту очередь соседа перехватывает
меньше чем за минуту, а по умолчанию ожидание реагирует не быстрее двух минут.

Полностью пустой карты можно не дождаться вовсе, поэтому порог занятости поднят
(`MAX_USED_MIB=25000`). Соседние очереди (`run_experiment.py` у zarutskiy) сами ограничивают
каждый свой процесс 45 % памяти карты и берут карту, когда свободно 45 % плюс гигабайт, то есть
рассчитаны на соседство. Наш прогон на Qwen2.5-3B занимает ≈29 ГБ из 81, вместе с чужим потолком
36 ГБ это 65 ГБ — обе задачи помещаются и друг друга не вытесняют.

```
tmux new-session -d -s fz-wait-bt "STEPS='01 02 03 04 05 06' INTERVAL=10 CONFIRM=2 \
  MAX_USED_MIB=25000 bash scripts/wait_and_launch.sh launch/qwen2.5-3b_beavertails-b1b5b6bv.sh 1"
tail -f results/qwen2.5-3b_beavertails-b1b5b6bv/logs/<последний>.log
```
